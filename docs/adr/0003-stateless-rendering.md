# ADR-0003. Рендер без хранения файлов

Дата: 6 ноября 2026.

## Контекст

На проде нет постоянного тома, а значит нельзя гарантировать сохранность PDF и SQLite между
рестартами и репликами. При этом клиент подписывает конкретные байты PDF, поэтому сервис обязан
отдавать стабильный, воспроизводимый результат.

## Решение

- `POST /api/v1/conversions` возвращает JSON с метаданными и короткоживущим `downloadUrl`.
- `GET /api/v1/downloads/{token}` отдаёт байты из in-memory кэша; токен — 32 случайных байта, TTL 15 минут.
- PDF и XML нигде не сохраняются: ни на диске, ни в базе.
- Одинаковые байты XML в пределах `CACHE_TTL_SECONDS` отдаются из in-memory LRU-кэша
  (`cached: true`), с ограничением `CACHE_MAX_BYTES`.
- Повтор определяется только содержимым: отдельного `Idempotency-Key` нет.
- Удалены `GET /api/v1/conversions/{artifactId}`, SQLite, TTL артефактов и хранение токенов на диске.
- `xmllint` использует приватный временный каталог в `os.tmpdir()`, который удаляется при остановке.

## Последствия

- Ссылка работает только в пределах TTL и только на том же инстансе; после рестарта она даёт 404,
  документ нужно запросить заново.
- Клиент обязан сохранить байты сразу после скачивания, если они нужны для подписи или архива.
- Кэш не разделяется между репликами; при горизонтальном масштабировании возможны повторные рендеры.
- Нет аудита «что именно было выдано»: остаётся только лог конверсии без содержимого.
- Требование к детерминизму усиливается: повторный рендер тех же байтов должен давать тот же
  `pdfSha256`, это проверяется integration-тестом после рестарта.

## Альтернативы

- **S3/внешнее хранилище** — сохраняет повторную выдачу и аудит, но требует инфраструктуры, которой нет.
- **tmpfs + SQLite** — переживает только жизнь контейнера, не решает аудит и усложняет деплой.
- **Полный отказ от кэша** — проще, но каждый повторный запрос запускает Chromium.
