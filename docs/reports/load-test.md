# Нагрузочный прогон

Дата: 3 ноября 2026. Стенд: Docker Desktop на Apple Silicon (macOS), контейнер `xmltopdf-api-1` с
ограничениями **2 CPU / 2 GiB**, `shm_size=256 MiB`, read-only rootfs, том `/app/data`; Chromium m156
внутри образа; Node.js 24; XSD-валидация через `xmllint`. Это испытательный бюджет, а не измеренный SLA:
машина не является закреплённым Linux-стендом, результаты зависят от хоста.

## Методика

- `scripts/load-test.mjs`: каждая итерация — отдельный `POST /api/v1/conversions` с binary XML, без
  переиспользования артефакта по содержимому; считаются все ответы, включая ошибки.
- Нагрузка задаётся числом одновременных воркеров и общим числом запросов; латентность — полное время
  HTTP-запроса, включая XSD, рендер и сохранение артефакта.
- RSS снимается `docker stats --no-stream` во время прогона (приблизительно, вместе с Chromium).
- Тяжёлые fixtures генерируются `node scripts/make-heavy-fixture.mjs <rows>` (синтетический УПД,
  валидный по XSD).

При параллелизме 5–10 запросы встают в очередь (2 активных рендера); пропускная способность упирается
в два одновременных Chromium-контекста, а не в XSD или диск.

### Тяжёлые документы (параллелизм 2)

| Документ | Страниц | PDF | Запросов | p50, мс | p95, мс | max, мс | Пик RSS |
| --- | --- | --- | --- | --- | --- | --- | --- |
| УПД, 100 строк | 7 | 121 КБ | 10 | 527 | 2 483 | 2 483 | 275 MiB |
| УПД, 1 000 строк | 55 | 378 КБ | 3 | 2 038 | 3 607 | 3 607 | 296 MiB |

1 000 строк укладываются в лимит 100 страниц (55 страниц) и не усекаются; общий deadline 30 с не
достигается.

### Перегрузка очереди

20 одновременных запросов при лимите `2 активных + 10 ожидающих`:

```
201: 12, 503 RENDERER_BUSY: 8, 500: 0
```

Очередь ограничена, лишние запросы получают `503` с `Retry-After`, зависших воркеров нет. Сервер
остаётся healthy после прогона.

## Соответствие целевой гипотезе

Спецификация задаёт ориентир: p95 до 10 секунд при `concurrency=2` на 2 CPU / 2 GiB. На этом стенде:
типовой УПД — **1,76 с**, 1 000 строк — **3,61 с**. Гипотеза выполнена с запасом, но это не заменяет
измерение на целевом Linux-железе.

## Воспроизведение

```bash
docker compose up -d --no-build
node scripts/make-heavy-fixture.mjs 1000 test-output/heavy/upd-1000-rows.xml
node scripts/load-test.mjs test/fixtures/upd-schfdop.xml 2 20
node scripts/load-test.mjs test-output/heavy/upd-1000-rows.xml 2 3
docker compose down -v
```

## Квота владельца

После прогонов добавлена квота `RATE_LIMIT_PER_MINUTE` (по умолчанию 300 запросов в минуту на
владельца). Все серии выше укладываются в неё; при повторных прогонах с тем же ключом учитывайте
окно и при необходимости задайте `RATE_LIMIT_PER_MINUTE=0` для стенда.

## Ограничения

- Один прогон, без прогрева и без статистики по нескольким повторам; p95 на 20 запросах чувствителен
  к единичным выбросам.
- Артефакты не удалялись между итерациями: TTL-очистка и рост `/app/data` отдельно не измерялись.
- RSS — приблизительный показатель контейнера, не разделён по процессам API и Chromium.
- Нагрузка на XSD отдельно не профилировалась (в логах `xsdMs` — единицы миллисекунд).
